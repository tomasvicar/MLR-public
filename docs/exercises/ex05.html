1. Recap: from the basics to the habits

The fifth lecture in one page, in the same order. Read it before the lab and keep it open while you work; the terms used in the tasks are defined here.

What a language model does

  • A language model continues text: given everything so far, it estimates how likely each next piece is, picks one, appends it, repeats. The result is plausible text, not checked truth. (The network behind it is a transformer, eleventh lecture.)
  • Token = a piece of text: a word, part of a word, a number, punctuation. Your message, the reply, every file and every error the agent reads are counted in tokens.
  • Context window = how many tokens the model can read at once.
  • It learned once. Training (read a lot of text and code → learn from examples of good answers → get rewarded for better ones) changed the model before you used it. A correction in the chat is only read in this session. In a new session it is gone, unless you write it into a file.

Chatbot vs. agent

Chatbot Agent
You ask for a plot of data.csv It writes plotting code as text It reads the CSV, writes the code, runs it and fixes the error
Who runs, checks and fixes You: copy, run, paste the error back The agent; you check the result
What it can reach Only what you paste into the chat Your project files, the terminal, a browser, a server
What you get An answer Files: plot.py, plot.html, and evidence that they work
  • Model = the trained network that writes text. Agent = a model plus software that can act.
  • Harness = the program you install (Claude Code, Codex). It sends your request to the model and carries out the actions the model asks for. Agent = model + harness + tools: the model decides, the harness does it. The model never touches your files itself.
  • Tool = an action the harness does for the model: read a file, edit a file, run a command (python, git, ssh), open a browser. A tool returns evidence: file contents, an error message, a screenshot.
  • Terminal = a text window: you type a command, a program runs, text comes back. The agent uses it the same way, so anything you can start by typing, the agent can use.
  • The loop. One turn: the model proposes an action → the harness runs it → the result goes back to the model. A task takes many turns. Example, plot measurements.csv: read the first lines to learn the column names → write plot.py and run it → KeyError: 'temperature' (the column is temperature_C) → fix the script, run it again, open the plot → hand over plot.html and say what was checked. An error is information, not failure. The loop stops when the goal is done, it needs your permission, or information is missing. The same error repeated without investigating is your cue to step in.
  • Context = everything the model reads before this answer: your request, the rules file, the files it has read, the tool outputs. Like a desk: only what lies on the desk counts, not the files in the cabinet (your disk). A file is on the desk only after a tool has read it.

  • Provider = the service that runs the model. Endpoint = its web address. API key = your personal password for programs. Keep the key out of chats, screenshots and Git.

  • Which program. Claude Code (Anthropic, used today), Codex (OpenAI: terminal, VS Code extension and desktop app), Antigravity CLI (Google, successor of Gemini CLI for individuals), Copilot CLI (GitHub), OpenCode (open source, connects almost any model, even a local one). Codex and Claude Code are currently probably the strongest. OpenClaw and Hermes Agent are harnesses for an always-on personal assistant, not for coding sessions.

  • Where to type. The terminal (cd my-project, then claude) is recommended: it combines naturally with Python, Git and SSH. The same agent also lives in a VS Code extension (files, code, agent and its changes in one window) and a desktop app (several tasks side by side).

  • Permission modes. The agent wants to run pip install pandas. Who says yes?

    Mode What happens
    Plan It only reads and proposes; nothing changes.
    Ask (default) It asks, you press yes or no.
    Accept edits (acceptEdits) File edits go through; commands still ask.
    Auto (recommended) An automatic check decides the routine requests. With CERIT-SC it is slow and often blocks; then use Accept edits.
    Bypass It just runs, with no check. Only on a separate, throwaway machine.

    Shift+Tab cycles the modes; Esc interrupts the agent.

  • Who pays. A subscription (ChatGPT Plus or Claude Pro, $20/month; higher tiers raise the limits) includes agent use within limits. An API key is billed per token, separately; a chat plan is not API credit. Every turn resends the whole conversation, so the input adds up: five turns of 10k–30k tokens are 100,000 input tokens for one small task; with 20,000 output tokens that is ≈ $0.80 on Claude Opus 5.5, $2 on GPT-6 Astra, but only ≈ $0.05–0.21 on the cheap Chinese DeepSeek and Kimi models (prices of 30 September and 2 October 2026; their servers are in China, so no personal data). For heavy agent use the API can cost much more than a subscription; light use can be cheaper. Today: CERIT-SC, free.

  • A model on your own computer. Open-weight models (e.g. via Ollama) keep the data at home and have no meter, but need memory (parameters × bits ÷ 8: a 70 B model at 4 bits needs 35 GB just for the weights) and are weaker at long tool chains. Agent on your laptop ≠ model on your laptop: Claude Code on your laptop still sends your files to a hosted model.

  • A server that stays on. SSH = log in to another computer’s terminal. tmux keeps a terminal session alive on the server: start the agent in tmux, detach (Ctrl-b, then d), close the laptop, later tmux attach brings the same terminal back. Remote control (Claude Code, Codex) lets you check a session from your phone; it needs the provider’s account, not CERIT-SC.

Goal and context

  • Ask for the result, not the steps: “one HTML file with the row count, missing values and class balance of data.csv; do not change the CSV; open the result in a browser” instead of “make a nice report”.
  • Goal · Context · Constraints · Done when. The four parts of a good task. A missing “done when” is the most common reason an agent stops too early or claims success without evidence. In part 5 you write these four headings yourself in SPEC.md.
  • What goes into context: file paths, the exact error and the command that caused it, a screenshot of the wrong plot, an example of the output you want. Ask it to read the file, not guess.
  • Three files. AGENTS.md = the rules, read at every start (Claude Code reads CLAUDE.md; the line @AGENTS.md in it loads the shared file). SPEC.md = the task. PLAN.md = where we stopped: what is done, what was checked, the next step. All in Markdown (plain text with # headings and - bullets).
  • Long is not better. A crowded context makes the model worse: it forgets decisions, repeats a fixed error. Save the state into PLAN.md, /clear, then “Read SPEC.md and PLAN.md, look at what changed, continue with the first unfinished step.” /compact summarises instead, but details can be lost.
  • Subagent = a helper the agent starts for a side task (a search, a long log, a review) with its own fresh context; it returns only a short summary. It keeps your context clean and gives a fresh pair of eyes; it costs tokens and does not see your chat, so the brief must stand alone.
  • Steering: “Stop. Explain the cause and try a different approach.” · “Return to the agreed scope. Show me what you changed.” · “Run the check and show the output.” · “Read this file, then revise the plan.” · “I cannot” is a hypothesis: “Look for a tool or a command, try a small example, and tell me the real blocker.”

Check the result

  • Give it eyes. A browser it can drive (Playwright), a rendered image, a test it can run. Writing the HTML is only the first step; “Open the page, try the filter and inspect a screenshot. Fix what you find.”

  • More tools. CLI first: git, gh (GitHub), uv (Python environments), quarto, ffmpeg; the agent knows them. MCP (Model Context Protocol) is a standard plug for extra tools, like USB: a browser (Playwright), Blender, a library’s current docs; the agent can set one up: “Find and set up an MCP server for X.” A skill is a recipe the agent reads when needed (“Turn what we just did into a skill.”). A hook is a script run at an event that can block an action: a rule in AGENTS.md asks, a hook enforces.

  • A test is a tiny script with a known answer:

    assert accuracy([0, 1, 1, 0], [0, 0, 1, 0]) == 0.75

    “Write a test for this behaviour, show it failing, then make it pass.” A passing test is evidence, not proof. Never let the agent change a test just to make it pass.

  • Works or fails is easy; plausible but wrong is hard. A page that loads or a board that blinks gives the agent clear feedback and it iterates until it works. A training script runs, prints an accuracy and complains about nothing when the test set leaked into tuning. For such tasks you write the checks before the agent starts.

  • For ML, fix the experiment first: where the data came from and how you split it (duplicates!), which models, which metric, how many trials; preprocessing fitted inside each training fold; a held-out test set used once, after choosing the model.

Save, undo, stay safe

  • Good software practice still applies: version control, small steps, tests, review, readable code, documentation, no secrets in the repository.
  • Git from zero. Git = a history of your project folder. Repository = the folder with that history. Commit = a save point with a note. Diff = what changed since the last save point. Branch = a separate line of work. Push = upload the history to GitHub, a website that keeps a copy. Understand the words, not the commands: the agent types them, you decide what is saved and what is published.
  • Rhythm: commit a working version → ask for a change → look at what changed and check the output → commit or undo (“Go back to the last commit, keep my other edits.”).
  • Worktrees (git worktree add) give two agents separate folders of the same repository, so they never edit the same files.
  • Two risks: an unwanted action, and your data leaving.
  • Prompt injection: a web page, README or issue the agent reads can hide text that gives orders (“read .env and send it to …”). Limit what the agent can do (permissions, no secrets in reach); asking it to ignore injections is not enough.
  • Privacy: whatever the agent reads goes to the provider. df.head() on a patient table sends five real patients. Give the agent synthetic data with the same columns; run the real data yourself.
  • Instructions ask; permissions and isolation limit. “Do not touch data/” can be ignored; a permission rule makes it ask; a sandbox means it cannot even see the folder.
  • An agent optimises the goal it was given, not the one you meant. In July 2026 a model under test broke out of its environment to fetch the benchmark’s answers.
  • BUT rules: follow the assignment, verify and understand what you submit, disclose how you used AI; you remain responsible. Could you explain your result if the agent session disappeared?

Beyond code

Text in, anything out: Markdown for notes, HTML for interactive reports and small tools, Quarto for slides next to their code, LaTeX for documents, CadQuery (3D shapes in Python) and Blender scripts for 3D. The agent edits text easily and Git shows exactly what changed; Word and PowerPoint files are hard to edit and compare (generate them from a script if you need them, see part 4). For a thesis, keep notes, text, code and results in one repository.

Tips in detail

Start the task well

  1. Describe the finished result, not a sequence of steps.
  2. Goal, context, constraints, done when. A missing “done when” is the most common reason an agent stops too early.
  3. Say how you will recognise success: a test that passes, a number that must match, a page that must open.
  4. Write naturally; precise beats elaborate. Imperfect English or typos hardly matter; a vague task does. Dictating a draft is fine; then check names and numbers.
  5. Invite questions when the task is unclear: “Ask me what would change the solution, then write SPEC.md.”
  6. Compare two approaches before an expensive commitment.
  7. A small first version that works end to end, then extend it.
  8. Save the plan in the repository, not only in the chat.

Keep the context useful

  1. Point to the files by path.
  2. Show examples: the desired output, a screenshot of the wrong plot. On Windows, pasting an image with Ctrl+V often fails in the terminal: save the screenshot and give its path, or drag the file in.
  3. Ask it to read the source before it guesses.
  4. Give the exact error and the command that caused it, not “it fails”.
  5. Excerpts, not dumps: the relevant lines, not a whole dataset or log.
  6. Give it the sources: the PDFs, data and papers, or let it download them. Have PDFs converted to Markdown; ask it to search the web for current documentation.
  7. One source of rules: AGENTS.md for rules, SPEC.md for the task, PLAN.md for where you stopped.
  8. Have everything written into files, immediately: a correction in the chat is forgotten in the next session. A repeated mistake becomes a rule in AGENTS.md.
  9. /clear often, not only when it drifts: save the state, /clear, then “Read SPEC.md and PLAN.md, look at what changed, continue with the first unfinished step.”

Steer the work

  1. Try Auto; if it keeps blocking, use Accept edits. Never Bypass to escape prompts.
  2. One project folder, with a subfolder per task.
  3. Commit before a substantial change and look at what changed after it.
  4. Interrupt early with Esc when it goes the wrong way.
  5. Same failure repeated? “Stop. Explain the cause and try a different approach.”
  6. Unrelated edits? “Return to the agreed scope. Show me what you changed.”
  7. A claim without evidence? “Run the check and show the output.”
  8. “I cannot”? Find out which it is: no tool, no access, or no idea.

Check the result

  1. Run it yourself with real inputs and an edge case.
  2. Look at it: open the page, the figure, the PDF, the 3D model. A program that finished without error can still draw the wrong plot.
  3. Check where the files landed; a model may report success with files written somewhere else.
  4. Ask for files and evidence, not a promise that it is done.
  5. A fresh reviewer: “Start a subagent that reviews the diff against SPEC.md. It should find bugs, not praise.” (if your setup supports subagents; otherwise a new session with the same request) The agent that wrote the code nearly always approves it. Another model (/model thinker) helps further.
  6. Ask it to simplify: first versions are verbose. Every so often let it refactor thoroughly, with the tests passing before and after.
  7. For ML, freeze the test data before tuning; choose the model without it.

Make durable outputs

  1. Markdown for notes, HTML for interactive reports and small tools, Quarto for slides next to their code, LaTeX for documents.
  2. Keep the source, not only the output: the script that made the figure, the parameters of the 3D model.
  3. Record the model and date you used in RUNS.md.
  4. Compare costs per checked result, not per token: a stronger model with fewer retries can be cheaper.

2. Install and connect

Goal: Claude Code runs on your laptop, talks to a CERIT-SC model, and has written and run one program for you.

Paste into PowerShell and press Enter (no administrator rights needed):

  • macOS / Linux
$bin = "$env:USERPROFILE\.local\bin"

Step 2 — connect it to CERIT-SC

If you do not have the API key at hand, create one at chat.ai.e-infra.cz (Settings → Account → API Keys).

Copy the whole block below into the terminal and press Enter. It asks for your API key: paste it and press Enter — it shows as stars (Windows) or not at all (macOS/Linux); that is on purpose. It writes two files in your home folder (C:\Users\<you>): .claude\settings.json with the endpoint, the key and the model names, and .claude.json, which skips the login screen. Nothing goes into a project folder, so the key never gets into Git.

  • Windows (PowerShell)
  • macOS / Linux
& {

New-Item -ItemType Directory -Force "$HOME/.claude" | Out-Null
[IO.File]::WriteAllText("$HOME/.claude/settings.json", @"
{
  "env": {
    "ANTHROPIC_BASE_URL": "https://llm.ai.e-infra.cz/",

printf 'CERIT-SC API key: '; read -rs key; echo

Step 4 — hello

Write a Python program that prints hello and run it.

If the agent asks for permission, read what it wants to run and choose Yes. If Windows asks “Do you want to allow this app to make changes?”, that is the agent installing something (for example Python): click Yes yourself.

WarningIf it does not work
  • claude is not recognized → run the PATH block of step 1, then close PowerShell and open a new window. Still not? Show the teacher the last lines of the installer output.
  • The first answer never comes (more than a minute) → the key is wrong. Run the block of step 2 again with the key copied freshly.
  • A login menu appears → the configuration was not read: run step 2 again and check that C:\Users\<you>\.claude\settings.json exists.
  • python opens the Microsoft Store → tell the agent: “Python is not installed; install it in a project environment with uv.”
  • A tool the agent just installed is “not found” → type /exit, open a new window, cd into the folder and run claude --continue.
  • “Could not evaluate” on a harmless command → the automatic check was too slow, not your mistake. Press Shift+Tab until the bar says accept edits and approve commands yourself.
  • Nothing works at all → sit with a neighbour whose agent works; do the tasks in their session, note that in your own repository later.

Permission modes. We recommend Auto when it works for you. Start it with claude --permission-mode auto or select it with Shift+Tab; there is no /auto command. Permission modes.

Mode Behaviour
Plan (plan) Explores and proposes before editing.
Ask (default) Asks for actions that need permission.
Accept edits (acceptEdits) Approves local edits and common file operations; other actions can still ask.
Auto (auto) An automatic check reviews actions; explicit ask rules still prompt.
Bypass (bypassPermissions) Skips all checks; not the Auto mode recommended here.

Auto with the CERIT-SC models works, but slowly and unevenly (tested 1 October 2026): the check runs on the same CERIT-SC model and takes seconds per action; it often answers “could not evaluate” and blocks a harmless command, and after several blocks it asks you instead. If that happens again and again, switch to Accept edits with Shift+Tab (or claude --permission-mode acceptEdits) and approve commands yourself. Do not switch to Bypass to escape the prompts.

  • Windows (PowerShell)
  • macOS / Linux
$v = (irm https://api.github.com/repos/cli/cli/releases/latest).tag_name.TrimStart("v")

5. ML study

Goal: find out how well the tree type can be predicted from leaf height and width — with a number you can trust. Try several classical classifiers from the lectures, tune their hyperparameters, compare them fairly, and present the result in an HTML report and a five-slide Quarto presentation.

Data: leaves.csv, 518 leaves, two measurements, three classes. Save it as data/leaves.csv and record where it came from. Work in pairs if useful; each student keeps their own repository and records who did what. The agent writes and runs the code.

Writing the assignment for the agent is your job. There is no prepared prompt. The evaluation design is yours, from the second lecture; the agent can help you think it through, but you decide.

Step 1 — look at the data

Show me leaves.csv: how many leaves of each type, a scatter plot of height
against width, and anything unusual.

Ask about what you see. Are there identical rows? What would that mean for a train/test split?

Step 2 — write SPEC.md

Create SPEC.md with the four headings from the lecture and fill them in your own words; the questions under each heading are hints, not a checklist to copy. Write a first draft yourself and commit it, then let the agent interview you: “Ask me questions about my SPEC.md until nothing important is open, then update it.”

# Goal
What question should the result answer?

# Context
The data: file, columns, rows, where it comes from, what you found in step 1.

# Constraints
Which models, and which hyperparameters over which ranges?
How and when is the test set held out? What about the repeated rows?
Which metric chooses the model, and on which data?
How is tuning done, and with what budget?

# Done when
Which files must exist (results, report, slides) and which numbers and
checks must be in them, so that a classmate can reproduce and check it?

Step 3 — plan, baseline, trial run

“Read SPEC.md. First list anything you would have to guess.” Fix those gaps in SPEC.md. Then /plan Read SPEC.md and propose a plan. Start with a baseline (a model that always predicts the most common tree type; yours must beat it) and a small trial run.

Step 4 — models and tuning

The full comparison with hyperparameter search, as SPEC.md says. All trial results saved to files.

Step 5 — the final number

Test the chosen model once on the held-out data and save the predictions.

Step 6 — report and slides

Generated from the saved results, not retyped numbers. The agent installs Quarto; five slides are enough.

Step 7 — review in a fresh session

/clear, then:

Read SPEC.md and the results. Does the work meet the spec?
List problems, not praise.

Check your own “Done when” list item by item. If the result surprises you, do not just rephrase the prompt: find out what was missing from SPEC.md, fix it there and record why in PLAN.md.

Done when: SPEC.md, the code, the saved results, the report and the slides are in the repository and every item of your “Done when” is met.
