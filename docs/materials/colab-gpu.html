Colab GPU from your agent

You write and keep the code on your own computer with an AI agent (Claude Code, Codex, …). When something needs a GPU, the agent sends the script to a free Google Colab T4 with Google's official colab CLI and brings the results back. Two skills tell the agent how: colab-gpu-setup (once) and colab-gpu (every time).

Why

Coding agents work best on your own computer: they see the whole project, edit files, run tests and keep everything in Git. Training a neural network, however, needs a GPU, and most laptops do not have a usable one. Google Colab gives a GPU for free, but only inside a notebook in the browser, where the agent cannot work and the code lives apart from the project.

This setup joins the two. The agent writes and tests the code locally, then hands only the heavy run to a Colab virtual machine with a GPU and downloads the results into the project. You stay in one place, the code stays in your repository, and the GPU costs nothing.

How it works

  1. The agent writes one self-contained job script and tries it on the CPU with a tiny setting, so mistakes are found before any GPU time is used.
  2. colab run --gpu T4 job.py starts a fresh Colab VM, sends the script, and streams its output back to the agent.
  3. On the VM the script downloads its data from a public URL, trains, and writes the model, metrics and plots into one zip file.
  4. The agent downloads the zip and stops the VM, so no GPU time is wasted.

The colab command is Google's official Colab CLI (google-colab-cli), not a tunnel or a workaround, so it is within the Colab rules.

Limits to know

  • The free tier gives a T4 (16 GB) when one is available; how much GPU time you get is not fixed and Google changes it with demand. When you run out, wait or use a paid Colab plan.
  • A VM lives at most a few hours and everything on it is lost when it stops, so the job must save its results and the agent must download them.
  • Data should come from a URL. Uploading from your disk works only for files up to about 75 MB.
  • You log in to Google once per computer yourself; the agent cannot do it.

# Setting up the Colab GPU

Goal: the `colab` CLI is installed and logged in, and a test job ran on a
Colab T4 GPU. Afterwards the skill `colab-gpu` describes how to run real
work. Go step by step and tell the user what you are doing.

## 1. Install the CLI

1. Check whether it is already there: `colab version`.
2. If not: `uv tool install google-colab-cli`. If `uv` is missing, install it
   first (`pip install uv`, or the installer from https://docs.astral.sh/uv/).
   If `uv` is then not found (pip put it into a `Scripts` folder that is not
   on `PATH`), call it as `python -m uv tool install google-colab-cli`.
3. If `colab` is then not found, the uv tool folder is not on `PATH` of the
   running shell. Linux/macOS: `export PATH="$HOME/.local/bin:$PATH"`.
   Windows Git Bash: uv installs into the Windows profile, which is not always
   `~` (on school computers `HOME` can be a network drive), so use
   `export PATH="$(cygpath "$USERPROFILE")/.local/bin:$PATH"`. Repeat the
   export in every new shell, or run `uv tool update-shell` once for new
   terminals.
   If `uv` fails with "untrusted mount point (os error 448)", pass a Python
   explicitly: `uv tool install google-colab-cli --python "$(uv python find)"`.
4. Windows, Git Bash: before every `colab` command that names a remote path
   (`/content/...`) run `export MSYS_NO_PATHCONV=1`; the skill `colab-gpu`
   explains why.

## 2. Login (the user does it, not you)

The login waits for a code typed in by a human, so you cannot run it. Run
every `colab` command yourself with `< /dev/null`, so that nothing can hang
waiting for input. Tell the
user exactly this:

> Open a new terminal (on Windows: Git Bash) and run `colab sessions`. It
> prints a URL. Open it, sign in with your Google account, allow access, copy
> the code and paste it back into the terminal. Then tell me "done".

The token is saved in the user profile on this computer, so this is needed
only once. When the user says done, check it without risking a
prompt that waits forever:

```bash
timeout 30 colab sessions < /dev/null
```

It must print "No active sessions found on server." (or a list of sessions)
without asking anything. If it prints a URL or times out, the login did not
work: ask the user to repeat it.

## 3. GPU check

Write `gpu_check.py`:

```python
import torch
print("CUDA:", torch.cuda.is_available())
print("GPU:", torch.cuda.get_device_name(0))
```

and run it on a fresh GPU VM (without `--keep` the VM is released when the
script ends):

```bash
colab run --gpu T4 --timeout 600 gpu_check.py
```

The output must contain `GPU: Tesla T4`. Then `colab sessions` must report no
active sessions; stop any leftover one with `colab stop -s <name>`.

If it fails with `Allocation refused`, no free GPU is available right now or
another session of the same account is running: check `colab sessions`, wait
a few minutes and retry. Never use a second Google account to get around it.

## 4. Report

Tell the user: the CLI version, that the login works, the GPU name, and that
no session is left running. Check that the skill `colab-gpu` is installed
next to this one (`.claude/skills/colab-gpu/SKILL.md`, or `colab-gpu.md` for
other agents); it is needed for the real work.

# Running code on a Colab GPU

The code is written and kept locally; only the execution happens on a Colab
virtual machine (VM). You drive the VM with the official Google Colab CLI
(`colab`).

## Before you start

If `colab` is missing or not logged in (`timeout 30 colab sessions < /dev/null`
asks for a login or times out), follow the skill `colab-gpu-setup` first.

**Windows, Git Bash:** always `export MSYS_NO_PATHCONV=1` before calling
`colab`, otherwise Git Bash rewrites the remote `/content/x` to
`C:/Program Files/Git/content/x`. With it set, give **local** paths as
relative paths (`job.py`, `out/results.zip`) or as `C:/...`, never `/c/...`.

## The rules

1. **Data come from a public URL and are processed in code.** The job script
   downloads the data itself into `/content/data/` (skip the download when the
   file is already there), unpacks and preprocesses them on the VM. Do not
   upload datasets from the local disk: `colab upload` sends a file in one
   request, and above about 75 MB the server drops it. Mounting Google
   Drive is not recommended: `colab drivemount` asks the user to grant
   access in a browser on every new VM, so the job cannot run on its own.
2. **One self-contained job script** (e.g. `job.py`): download data →
   preprocess → train → evaluate → write everything to `/content/out/`
   (model weights, `metrics.json`, plots as PNG) and at the end pack it:
   `shutil.make_archive("/content/results", "zip", "/content/out")`.
   It must also run on the CPU with a tiny setting, so that you can
   smoke-test it locally first:
   `device = "cuda" if torch.cuda.is_available() else "cpu"`, and an
   environment variable or argument such as `EPOCHS=1`.
3. **Smoke-test on a CPU first** (1 epoch, small subset): locally, or, when
   PyTorch is not installed locally or the disk is full, on a Colab CPU VM
   (`colab run` without `--gpu`, no GPU quota used):
   `colab run --timeout 1200 job.py --epochs 1 --subset 512`. Only a script
   that passed the smoke test goes to the GPU.
4. **`--timeout` is the total run time in seconds, and the default is only
   30.** Always pass more than the whole job needs (e.g. `--timeout 7200`).
   It is not an inactivity limit and it does not stop the script: when it
   runs out, the output keeps streaming, the script finishes on the VM, and
   only then may the CLI fail with `TimeoutError: Timeout waiting for reply`.
   Print progress with `print(..., flush=True)` once per epoch so that you
   (and the user) see it is alive.
5. **Always release the VM**: `colab run` without `--keep` does it itself;
   otherwise finish with `colab stop -s <name>`. Check `colab sessions` at
   the end — it must say no active sessions. Idle VMs eat the user's free GPU
   quota.
6. **Read the output for errors.** `colab exec` returns exit code 0 even when
   the script raised an exception or called `sys.exit(3)`; look for
   `Traceback` / `Error` in its output. `colab run` returns 1 on an exception
   and N on `sys.exit(N)`. Tracebacks come with ANSI colour codes; strip them
   with `2>&1 | sed 's/\x1b\[[0-9;]*m//g'`.
7. **Call `colab` with `< /dev/null`**, so that no command can hang waiting
   for input.

## Two ways to run

**A. One-shot job (preferred)** — a fresh VM, run, download, release:

```bash
colab run --gpu T4 --timeout 7200 --keep -s job job.py --epochs 30
colab download -s job /content/results.zip out/results.zip
colab stop -s job
```

All `colab` options go **before** the script; everything after it is passed
to the script as `sys.argv[1:]` — except `--timeout`, `--env`, `-s`,
`--keep`, `--gpu`, which `colab` takes for itself even there, so do not give
the script options with those names. `--keep` keeps the VM alive after the
script so you can download the results; without it the VM (and
`/content/out`) is gone when the script ends. `colab download` copies one
file (no directories), hence the zip; `colab ls -s job /content/out` lists
files. Script output goes to stdout, the `[colab]` messages to stderr.

**B. Interactive session** — when you iterate on the same loaded data:

```bash
colab new -s work --gpu T4
colab exec -s work --timeout 7200 -f job.py      # local file, sent to the kernel
colab exec -s work --timeout 600 -f analyse.py   # variables from job.py are still there
colab download -s work /content/results.zip out/results.zip
colab stop -s work
```

In `exec` the code runs inside a Jupyter kernel: `sys.argv` is not the
script's, so pass settings via `--env KEY=VALUE` (sets `os.environ`, which
then stays set for later `exec` calls) or variables in the code. Kernel state
(imports, loaded data, the model) persists between `exec` calls in the same
session; a `colab run --keep` session can be continued with `exec` the same
way.

## When something fails

- `Allocation refused (precondition failed)` on `colab new`/`run`: a GPU is
  not available right now or another session is still running. Run
  `colab sessions`, stop what is left, wait a few minutes and retry. Do not
  switch to another Google account (against the Colab rules). As a fallback
  run on the CPU with a smaller setting and tell the user.
- `TimeoutError: Timeout waiting for reply`: the job took longer than
  `--timeout` (see rule 4). The script has most likely finished anyway: check
  with `colab ls -s <name> /content/out` and download the results. Next time
  pass a larger `--timeout`.
- `exec`/`run` waits until the code ends, whatever `--timeout` says, so a
  script stuck in a loop hangs the command, and the next `exec` waits behind
  it (`colab status -s <name>` shows `BUSY`). Kill the command, then
  `colab restart-kernel -s <name>` (loses the variables, keeps the files),
  or `colab stop` and start again.
- Never run `colab repl`, `colab console`, `colab auth` or `colab drivemount`
  yourself: they wait for a human.
- More commands: `colab help`, `colab <command> --help`, and Google's own
  agent guide `colab skill`.

## Colab rules to respect

Free Colab forbids SSH/remote-desktop tunnels and using several accounts to
get around limits (https://research.google.com/colaboratory/faq.html). The
`colab` CLI is Google's official tool, so it is fine; do not install tunnel
tools (ngrok, cloudflared, colab-ssh).
